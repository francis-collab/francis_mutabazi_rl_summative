# RwandaCropGuard — Mission-Based Reinforcement Learning

**Course:** Machine Learning Techniques II — Summative  
**Mission:** Support crop health and food security in Rwanda through early disease detection, treatment, irrigation, community response, and timely harvest.

## 1. Assignment alignment

The assignment requires a custom mission environment with a relevant action space, observation space, reward function, start state, terminal conditions, and an advanced visualization; it also requires DQN, REINFORCE, PPO and A2C to interact with the same environment, plus at least 10 hyperparameter combinations per algorithm. The five-minute demonstration should use approximately three-quarters of its duration for the agent running in the environment.

This project implements a six-plot, 90-decision-day farm mission. The latest trajectory is generated by the trained PPO checkpoint and ends with the agent's **HARVEST** action.

## 2. Mission environment

`RwandaCropGuardEnv` models six mixed-crop plots:

| Plot | Crop |
|---|---|
| 1 | Beans |
| 2 | Maize |
| 3 | Cassava |
| 4 | Beans |
| 5 | Maize |
| 6 | Cassava |

The eight actions are:

1. `INSPECT` — inspect the current plot once.
2. `APPLY_ORGANIC` — apply organic disease treatment to the current plot when needed.
3. `APPLY_CHEMICAL` — apply chemical treatment to the current plot when needed.
4. `IRRIGATE` — draw from the shared water point and irrigate all six plots.
5. `MOVE_NEXT` — move to the next plot after inspecting the current plot.
6. `ALERT_COMMUNITY` — request community assistance once when disease risk or the late-season condition justifies it.
7. `WAIT_MONITOR` — allow the crop season to progress after all six plots have been inspected.
8. `HARVEST` — harvest the farm after maturity.

The observation has 26 values: current-plot one-hot encoding, six disease values, six soil-moisture values, weather, input/labour levels, season progress, yield risk, water reserve and community-alert status.

The reward encourages inspection, effective treatment, irrigation when the farm is dry, and successful harvest. It penalizes wasted inputs, repeated community alerts, premature harvest and missing the season deadline.

### Mission constraints and terminal logic

- Each plot is inspected once before the agent can move on from it.
- The agent cannot repeatedly collect the community-alert reward: the alert is a one-time action.
- Irrigation is a farm-wide operation and consumes one unit from the shared water reserve.
- Treatment actions are valid only when the current plot's disease severity justifies them.
- Harvest becomes available on day 78.
- On the final decision day, `HARVEST` is the only valid action. This is an action mask, not an automatic harvest: the policy still selects the action.
- Harvest terminates successfully; reaching the 90-day deadline without harvesting truncates the episode.

These constraints prevent the previous reward loophole where the policy repeatedly selected `ALERT_COMMUNITY` instead of completing the mission.

## 3. Three.js visualization

Open `visualization/viewer_3d.html` through a local web server. The viewer uses a clean Rwandan hillside farm image as the landscape foundation and overlays interactive Three.js elements.

It includes:
- A humanoid agent anchored at foot level and routed along the farm passages.
- Six crop plots with beans, maize and cassava plant models.
- Crop growth that changes with the recorded simulation day and each plot's moisture/disease state.
- Visible stubble after harvest.
- A shared water point and irrigation spray effects across all six plots.
- Hot/sunny weather cues when the weather index is high.
- Chemical and organic treatment spray effects.
- Six villagers who appear only after a community alert and walk toward the farm along the passage network.
- Play/pause, reset, speed control, plot selection, pan and zoom.

The viewer reads `assets/trajectories/latest_trajectory.json`. It does not invent agent actions: run the policy first to generate the trajectory, then open the viewer.

## 4. Setup with `uv`

The repository pins Python 3.12 in `.python-version` for the locked TorchRL dependency set.

```bash
uv python install 3.12
uv sync
uv run main.py --mode demo
```

The main requirement is a valid `pyproject.toml` and a clone-and-run workflow using `uv sync` followed by `uv run main.py`.

## 5. Run the best-performing updated agent

The full 40 experiments evaluation selected DQN as the best-performing algorithm.

```bash
# Run the dqn algorithm and record a trajectory for the Three.js viewer.
uv run main.py --mode play \
  --model models/dqn/best_model/dqn_model.pth \
  --episodes 1 --viz 3d --delay 1.2

# Serve the repository root.
uv run python -m http.server 8000
```

Open:

```text
http://localhost:8000/visualization/viewer_3d.html
```

The Python play command prints the agent's decisions and rewards in the terminal. The viewer plays the saved trajectory at a default pace of about 1.35 seconds per recorded decision. The current 80-frame DQN trajectory takes approximately 1 minute 47 seconds to play.

## 6. Hyperparameter experiments — important

The earlier experiment artifacts were produced against previous environment versions (different observation dimensions and reward/action rules). They are retained for traceability but must **not** be presented as the final comparison for this six-plot, 26-observation environment.

After `uv sync`, rerun the required 10 hyperparameter combinations for each algorithm:

```bash
# Full study: 10 configurations × 4 algorithms = 40 runs.
uv run run_experiments.py --device cpu --total-steps 80000

# Or run one family at a time.
uv run run_experiments.py --device cpu --only dqn --total-steps 80000
uv run run_experiments.py --device cpu --only reinforce --total-steps 80000
uv run run_experiments.py --device cpu --only a2c --total-steps 80000
uv run run_experiments.py --device cpu --only ppo --total-steps 80000
```

The experiment selector now ignores checkpoints whose observation dimension does not match the current 26-value environment.
